# Screenshot testing

The image-vector migration sample uses Roborazzi and Robolectric to render
selected Compose previews on the Android host JVM. Baseline previews live beside
the UI they exercise and are selected explicitly with
`@PreviewScreenshotBaseline`.

## Run locally

Use JDK 21 and run the focused tasks from the repository root:

```shell
./gradlew :samples:image-vector-migration:recordRoborazziDebug \
  -Proborazzi.cleanupOldScreenshots=true

./gradlew :samples:image-vector-migration:verifyRoborazziDebug

./gradlew :samples:image-vector-migration:compareRoborazziDebug
```

`record` replaces the generated reference set. `verify` fails when a fresh
render differs from that set. `compare` writes the fresh render and visual diff
without replacing the reference.

All generated files are disposable build output:

| Output | Location |
| --- | --- |
| Generated preview test source | `samples/image-vector-migration/build/generated/roborazzi/` |
| Generated baselines | `samples/image-vector-migration/build/roborazzi/baselines/` |
| Actual and comparison images | `samples/image-vector-migration/build/outputs/roborazzi/` |
| HTML report | `samples/image-vector-migration/build/reports/roborazzi/` |
| Test and comparison data | `samples/image-vector-migration/build/test-results/` |

Do not copy these files into `src` or commit them to development branches. CI alone
publishes visual-change PNGs and a Markdown report to temporary report branches; the
normal build can delete and regenerate the local output.

## Add a baseline preview

Keep previews beside the composable they exercise. Use the shared multi-preview
annotation for compact and expanded coverage, then opt stable visual contracts
into screenshot testing:

```kotlin
@PreviewScreenshotBaseline
@PreviewSymbolsScreen
@Composable
private fun ExamplePreview() {
    Example()
}
```

The scanner checks the normal feature package but captures only functions marked
with `@PreviewScreenshotBaseline`; ordinary development previews are ignored.
Keep preview state local and deterministic, without network or clock input.

## CI comparison

`.github/workflows/screenshots.yml` records the pull-request render, checks out
the pull request's base commit into a temporary worktree, and records the base
render on the same GitHub-hosted `macos-15-intel` runner. It then restores the base images as the
reference set and runs `compareRoborazziDebug` against the pull-request code.
This avoids comparing images generated by different operating systems.

## Public PR reports

Same-repository PRs with visual changes get a `roborazzi-pr-<number>` companion
branch containing:

- comparison images for changed screenshots, falling back to the PR image when
  comparison output is unavailable;
- PR images for added previews and base images for removed previews;
- a README and small source/outcome metadata file.

Unchanged previews are omitted from both the comment and published image set.
Roborazzi comparison output takes precedence over PNG byte differences: a
successful comparison does not report metadata-only changes. Added and removed
preview profiles remain visible even when the comparison succeeds.

One bot comment uses the **Roborazzi Visual Comparison** format: outcome, compared
base, workflow link, change count, and collapsed Added, Modified, and Removed
profile groups. Each row identifies the source file, preview, and variant, with
one report image. The first 25 rows in each group embed 360-pixel-wide images;
remaining rows link to their images. The comment links the complete change report
and GitHub's on-demand ZIP archive of the branch. Images use public
`raw.githubusercontent.com` URLs pinned to the report commit, so anonymous readers
can view them and force-updates cannot show cached images from an older run.
The scope remains the marked previews in `samples:image-vector-migration`.

When comparison passes without visual changes, CI creates no new comment. It
updates an existing report comment to the no-change result and deletes any stale
companion branch.

Reports use Git blobs, **not Actions artifact/cache storage**, and do not add PNGs
to development-branch history. Every update creates a root commit without parents
and replaces only that PR's report ref. The close-event cleanup workflow cancels an
in-flight producer using the same concurrency group, removes the report branch,
and retires the image links in the comment. GitHub may retain unreachable objects
or cached images after deletion; this is not a private or instant-erasure channel.

## Approval and failures

Changed, added, and removed screenshots require human review. Inspect every image
for the current head/base pair, then add `ui-review-approved`. Adding or removing
that label reruns the check; other label events skip screenshot work without
cancelling an active comparison.
Same-repository publishing removes a stale approval when the previous report was
for a different head/base pair. It never applies approval automatically.

Compare-only mode writes diffs without failing solely because pixels changed.
A failed comparison task remains a technical failure, even if some diff images
exist or the approval label is present. Failed recording never publishes a partial
report as complete. If neither revision produces screenshots, reporting fails
instead of silently reporting success. A base that predates screenshot support is
represented as an empty baseline, so new previews are reported as added.

Publishing checks that the PR is still open and its head/base pair is current. PNG
inputs cannot be symlinks, and reports reject unexpected files and oversized data
(10 MiB per image, 50 MiB per report). Only PNGs, README, and metadata are published;
logs, HTML build reports, secrets, and arbitrary build output are excluded.

Public fork PRs still render and compare on ephemeral hosted runners, but their
read-only token cannot publish report branches or comments. No privileged
`pull_request_target` workflow executes fork code. For automatic public image
reports, a maintainer must bring the change into a trusted same-repository branch;
otherwise reproduce the comparison locally. Ordinary CI remains read-only; only
the same-repository reporting/cleanup path needs content and PR write permissions.

## Reproduce locally

To reproduce a PR comparison, use a clean checkout of its head and a separate
worktree at its base SHA on the **same local machine** (prefer macOS 15, JDK 21):

```shell
# Replace BASE_SHA with the PR's base commit. Configure SYMBOLS_PYTHON first.
git worktree add --detach /tmp/symbols-visual-base BASE_SHA
(cd /tmp/symbols-visual-base && ./gradlew \
  :samples:image-vector-migration:recordRoborazziDebug \
  -Proborazzi.cleanupOldScreenshots=true)
```

Copy `/tmp/symbols-visual-base/samples/image-vector-migration/build/roborazzi/baselines/`
to the head checkout's `samples/image-vector-migration/build/roborazzi/baselines/`,
replacing any old baseline set. In the head checkout, run
`./gradlew :samples:image-vector-migration:compareRoborazziDebug --rerun-tasks`
and inspect the HTML report and comparison images listed above. Remove the
temporary worktree when done. This also provides a fallback when report publishing is unavailable.

Pixel output depends on the operating system, graphics stack, fonts, and JDK.
Local recording is useful for development, but the same-runner CI comparison is
the authoritative pull-request result. Keep the runner image stable; when it is
intentionally upgraded, review the complete local screenshot output rather
than blindly approving a bulk diff.

See the upstream [Roborazzi preview support and task documentation](https://github.com/takahirom/roborazzi#experimental-compose-preview-support)
for the underlying generated-test behavior.
